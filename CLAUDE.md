# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Web app that turns a Hebrew dialogue scene (PDF or DOCX) into a filled-in analysis spreadsheet, exported as PDF. Drag-and-drop UI; no persistent storage. Each request is parsed, classified into name / stage-direction / dialogue items, written into the template `טבלת ניתוחים ריקה.xlsx` (column B), and converted to PDF via headless LibreOffice.

## Commands

Activate the venv first: `.\.venv\Scripts\Activate.ps1`

- Install deps: `pip install -r requirements.txt`
  - `requirements.txt` is complete and is the single file for local dev and the Lambda image. Two pins matter: `python-bidi<0.5` (0.6+ needs a Rust toolchain on Python 3.14) and `Pillow` (the row-height estimate in `filler.py` measures glyph widths with it; pdfplumber only pulls it in transitively, so it is pinned explicitly).
- Run dev server (hot-reload): `$env:DEV_KEEP_OUTPUTS=1; uvicorn app.main:app --reload --host 127.0.0.1 --port 8000`
  - Open http://127.0.0.1:8000/ for the UI; POST to `/api/convert`; `/health` for liveness.
  - **Always run with `--reload`** during development. Without it the server keeps serving old code after edits, which has burned multiple debugging sessions.
  - `DEV_KEEP_OUTPUTS=1` makes every successful conversion drop a copy of the filled `.xlsx` and the produced `.pdf` into `tests/`, named after the input file's stem. Lets you inspect what LibreOffice was fed vs. what it produced when the PDF looks wrong but the xlsx looks fine.
- Quick parser+filler+export sanity check: `python debug_parser.py` (regenerates `_w7_*.xlsx` / `.pdf` / `.png` for the two sample files in the repo root).
- End-to-end HTTP test (server must be running): `python test_e2e.py`
- Batch review: `python batch_convert.py --out <name> <dir-or-files>` converts every scene through the full pipeline into `ניתוחים בדיקה/<name>/` (one `<stem> - ניתוח.pdf` per source) and writes a `_report.txt` with per-file item counts and per-page fill, so a broken page is visible before opening anything. The review corpus lives in `בדיקה מקור/` (not committed; ~100 real scene files) and the reviewer's categorized outputs in `ניתוחים בדיקה/אישה וגבר/` (`תקינים`, `טקסט חתוך`, `הערות בימוי לא מופרדות מטקסט`, …). Re-run the batch and diff item counts against the previous run before touching the parser guards or the row-height math.
- Per-stage tests: `test_parser.py`, `test_filler.py`, `test_pdf_export.py` — each is a plain script run via `python <name>.py`, not pytest, and none of them asserts anything; they just exercise a stage. `test_filler.py` currently fails at startup because its sample (`Dead Poets Society - טוד וניל.pdf`) is not in the repo. The batch review below is the real regression check.

LibreOffice (`soffice`) must be installed and discoverable. `app/pdf_export.py` searches `SOFFICE_BIN` env var → `PATH` → standard Win/Linux/macOS install paths, in that order.

## Architecture

Pipeline (one request flows top to bottom; no shared state):

1. **`app/main.py`** — FastAPI app. `/api/convert` streams the upload into a per-request `TemporaryDirectory` (25 MB cap, extension whitelist), invokes the pipeline, returns the PDF as a `FileResponse` with a `BackgroundTask` that wipes the tmpdir after the response is sent. Static UI is mounted at `/` *after* the API routes so `/api/*` and `/health` win.
2. **`app/parser.py`** — Thin dispatcher that routes by file suffix to:
   - **`app/parser_pdf.py`** — pdfplumber + bidi extraction.
   - **`app/parser_docx.py`** — python-docx extraction (with raw-XML fallbacks for Hebrew complex-script bold).
   - **`app/parser_common.py`** — shared types (`LogicalLine`) + post-extraction pipeline (`_classify`, `group_into_items`, `trim_preamble`, `fix_reversed_brackets`, `clean`).

   Both format parsers produce `list[LogicalLine]` and feed it through the same `lines_to_items` pipeline → `list[{"type": "name"|"stage_direction"|"dialogue", "text": str}]`.
3. **`app/filler.py`** — Items → filled `.xlsx` written to disk. Computes per-row heights, applies fonts/alignment, and emits manual page breaks.
4. **`app/pdf_export.py`** — `.xlsx` → `.pdf` via `soffice --headless --convert-to pdf`. Each invocation uses an isolated `UserInstallation` profile so concurrent requests don't collide.

The template (`טבלת ניתוחים ריקה.xlsx`) lives at the repo root and is the single source of truth for header rows, fonts, and column widths. Data starts at row 5, column B; columns A/C/D/F hold static labels and grid lines; E is widened at fill time to absorb leftover horizontal space.

The static UI (`app/static/index.html`) renders a full-width magenta `.hero` band (33vh tall) at the top, displaying `logo-chubbuck-wide.png` with `object-fit: cover; object-position: center`. The logo PNG was pre-padded to a 5.33:1 aspect ratio with the magenta background (`#C33552`) baked in, so `cover` crops only flat magenta on either side regardless of viewport width — both the wordmark and the Hebrew brand line stay centered and visible without white borders.

### Hebrew / RTL handling

- **PDF extraction (parser_pdf.py)**: pdfplumber gives chars in *visual* order without reliable space chars. We rebuild lines via `_reconstruct_line_text` (insert space wherever the x-gap > `_WORD_GAP_PT`), then run the text through `bidi.algorithm.get_display(..., base_dir='R')` to flip into logical order, then pass through `clean` regexes that fix punctuation spacing and stray-letter splits common to Hebrew PDFs.
- **DOCX extraction (parser_docx.py)**: bold/underline detection has three layers, in order: (1) **font name** — many real-world Hebrew screenplays don't set `<w:b>` at all and instead pick a heavy face directly (e.g. "Assistant ExtraBold"), so we check the run's `w:rFonts` for substrings like 'bold', 'black', 'heavy', 'extrab' (same heuristic as the PDF parser); (2) **direct toggles** read from raw XML — both `<w:b>` and the complex-script variant `<w:bCs>` that Hebrew runs use, since python-docx exposes only `w:b` (so a Hebrew-only doc with a real bold toggle reads as None across the board); (3) **inheritance** — walk `run.style` and `paragraph.style` chains via `base_style`. A line counts as bold/underlined only when *every* non-whitespace run carries the property.
- **Bracket repair**: some PDFs encode bracket pairs in visual order so they swap after bidi normalization; `_fix_reversed_brackets` detects this per-pair across the whole document.
- **Cell formatting (filler.py)**: every cell gets `Alignment(readingOrder=2, ...)` to force RTL reading order regardless of the cell's bidi base direction.
- **Classification**: `name = bold + underlined`, `stage_direction = bold only`, `dialogue = neither`. Underline detection scans `page.rects` and `page.lines` for thin horizontal strokes overlapping the line bbox; the search window straddles the baseline (`UNDERLINE_Y_ABOVE=8`, `UNDERLINE_Y_BELOW=4`) because PDFs place the underline above the bbox bottom.
- **Right-edge geometric promotion** (`_annotate_right_aligned_lines` in parser_pdf.py): some screenplays don't bold their stage notes — they're just full-width right-aligned paragraphs (e.g. "ריימונד לא זז" between two character turns) while dialogue sits in a narrow centered column. After extraction we compute the doc's right text margin (`max(line.x1)` across non-watermark lines) and flag any unbold line whose `x1` lands within `_RIGHT_EDGE_TOLERANCE_PT = 20.0pt` of it. (Centered lines are deliberately *not* excluded per-line — see the centered-block guard below.) `_classify` treats `right_aligned=True` as a third stage_direction condition. 20pt tolerance covers pdfplumber bbox jitter (observed: a Rain Man stage direction at `x1=492.8` vs the doc's 508.7 margin). No width minimum: short single-line stage notes sit at the margin too and a width filter loses them.
- **Centered-block guard** (`_CENTERED_BLOCK_RATIO_THRESHOLD = 0.75` in parser_pdf.py): a *center-justified* script sets dialogue with equal left and right margins, so the long lines of a speech reach the right margin and get promoted, while the short last line of the same speech doesn't — splitting one speech into a bogus `stage_direction` plus a `dialogue` tail. The ratio guard below doesn't catch it: in `בנות גילמור` only **22%** of unbold lines reach the margin (the many short single-line replies dilute it), just under the 25% threshold. Centering is the discriminator, but **only at document level** — a genuinely right-aligned line has its right edge pinned to the margin and a ragged left edge (Rain Man: right gap 86.6–86.8pt across nine notes, left gap 235–453), while a centered line's edges move together (Gilmore: right gap 92–108). A single *full-width* line is inherently ambiguous — equal margins make it read as centered **and** right-aligned — so judging per line loses two real notes in Raging Bull. So we judge the block: when ≥75% of the near-edge lines are centered, the "right margin" we found is really the page's center-justified text block and the blanket promotion is skipped. Observed centered shares: 0% (Rain Man), 29% (Raging Bull), 100% (Gilmore); 75% sits well clear of both sides. `_is_centered` is therefore computed for **every** line, not just bold ones — `_classify` only consults it under `bold`, so this doesn't affect name detection. Cross-check that fixed this: `כחול` exists as both PDF and DOCX; the geometry path used to give 154 items / 9 stage_directions against the DOCX metadata path's 151 / 5, and now agrees with it exactly (151 items, 100% type-sequence match).
  - **Per-line rescue under the block guard** (`_rescue_uncentered_near_edge`): the block guard fires on *every* PDF in the 42-file review corpus (centered share ≥ 0.75 everywhere), which silently switched the right-edge promotion off for PDFs. Most don't need it (bold stage notes), but אופוריה lost two real notes that are unambiguous on their own: pinned to the margin with a ragged left edge (`centered=False`, x0=350/367 against a 505 margin). So when the block guard fires we still promote near-edge lines that are **not centered**, with one extra condition — the line directly above must not itself be an unbold near-edge line. Without it the rule manufactures fragments: the short second line of a two-line note whose first line is full-width and reads as centered (סיינפלד: "ערוצים ללא הפסקה" under "ג'רי ואיליין יושבים על הספה…"), or the last line of a speech (על הספקטרום: "תקווה."). Corpus effect: exactly the two אופוריה notes recovered, nothing else changes. The rescue is deliberately **not** applied under the justified-doc guard: in RTL justified dialogue the last line of every paragraph is right-pinned and ragged-left, so it would promote speech tails (חצות בפריז, ratio 0.58, keeps its two real notes lost for now).

- **Justified-doc guard**: if more than `_JUSTIFIED_DOC_RATIO_THRESHOLD = 25%` of unbold lines reach the right margin, the doc is using justified dialogue (literary-script formatting where long paragraphs stretch to fill the full text width) and the geometric promotion is skipped entirely — geometry can no longer tell stage notes from dialogue. Observed ratios across test files: 6% (Raging Bull), 18% (Rain Man), 38% (justified Eyal Katan); 25% sits cleanly between. Cost of the guard: in justified docs, only bold stage_directions are detected — better to lose the rare opening stage note than to scatter half the dialogue into stage_direction.
- **Right-alignment promotion for DOCX** (`_annotate_right_aligned_lines` + `_paragraph_right_default` in parser_docx.py): the DOCX analog of the PDF right-edge rule, using Word's explicit paragraph alignment instead of x-geometry (DOCX lines have no coordinates). In these scripts dialogue and character names are explicitly **centered** (`w:jc=center`) while unbolded stage notes sit at the paragraph default or the start edge — the right margin for RTL text. `_classify` already treats `right_aligned=True` as stage_direction, shared with the PDF path.
  - **Which `w:jc` values mean "right margin" depends on the paragraph direction.** Transitional OOXML keeps the legacy `left`/`right` values with *logical* meaning — `left` is the start edge, `right` the end edge (ISO/IEC 29500-4, ST_Jc) — so on an RTL (`<w:bidi>`) paragraph Word stores a visually right-aligned stage note as `w:jc="left"`. The review corpus has 55 such lines (אהבה נושכת, בעלי ברית, יחסים פורנוגרפיים, נאמנות גבוהה…), every one on a bidi paragraph, and zero `right`+bidi lines. The first version of this rule excluded `LEFT` outright and so missed every one of them — the "stage notes not separated" bucket of the review. Accepted now: unset (`None`, the RTL default — bidi may live in `w:docDefaults` rather than on the paragraph, as in מרד הנעורים), `RIGHT`, and `LEFT` when the paragraph is RTL (`_paragraph_is_rtl` walks paragraph → style chain → document defaults). `JUSTIFY`/`CENTER` and `LEFT` on an LTR paragraph are never the signal.
  - **Guard threshold is 0.5, not the PDF's 0.25.** Same justified-doc rationale (if dialogue itself is right-aligned/default, nearly every unbold line is flagged and the signal is worthless), but the DOCX populations are far apart: highest legitimate share in the corpus is 0.27 (scripts dense with one-line stage notes), a default-aligned-dialogue doc would score ~1.0. At 0.25 the guard fired on האחים סיסטרז at 0.26 and cleared all 13 real notes. Docs whose dialogue is *justified* (מגדלים באוויר, נערי בייקר) never reach the guard — `JUSTIFY` isn't flagged in the first place.
  - **Known limitation:** the signal is authoring-convention, not semantics — a dialogue line the author forgot to center (identical font/size/no-italic to a real stage note) is indistinguishable and will be promoted (observed: one line in מרד הנעורים). Character-bio or premise paragraphs set the same way (אהבה נושכת, נאמנות גבוהה) are promoted too and survive the preamble trim as a leading stage_direction block. A positional heuristic ("first line after a name = dialogue") was rejected because legitimate stage notes also follow names and it would regress the PDF path.

- **Preamble trim** (`trim_preamble` in parser_common.py): scenes commonly start with a bold+underlined **scene title** (e.g. "כאב אמיתי") and one or more credit/metadata lines before the first character speaks. We must not render any of that. The trimmer anchors on the *first name that recurs* — real characters speak several times per scene, titles appear exactly once — and drops everything before it. A leading run of stage_directions immediately above that anchor is kept (those set the opening scene). Two rules that look right and aren't: anchoring on "first dialogue, then walk back to a name" fails because the credits line under the title classifies as `dialogue`, so the title becomes the apparent first name and nothing gets trimmed; anchoring on "first `name` followed (through any `stage_direction`s) by a `dialogue`" fails on the same shape — title(name) → credits(dialogue) matches at index 0 (observed in `21 גרם.pdf`, which opens `דיאלוג זוג - מתוך: "Grams 12"` → `בימוי: Alejandro…`). That rule survives only as the fallback for when no name recurs at all.
  - **Recurrence is counted on `_name_identity`, not raw text** — the name with its parenthetical cue stripped (everything from the first bracket char onward; both orientations, since `fix_reversed_brackets` runs *after* the trim). Scripts re-cue the same character on nearly every turn — `קב"שית` / `קב"שית (לדפי)` / `קב"שית (לזוהר)` / `קב"שית (בחוסר אמון)` — and comparing raw text makes each turn a distinct one-off name. Symptom when this breaks: the anchor slides to whichever character happens to be cued *bare* twice and the scene's opening exchanges get trimmed away as preamble (observed in `אודישן_לדמות_קבשית.pdf`: anchored on the 6th item's bare `זוהר`, silently dropping the opening stage direction and the first four exchanges). A name that is *only* a cue falls back to its full text, so two such names don't both collapse to `""` and read as a repeat of each other.
- **Wrapped character cues** (`_has_open_cue` in parser_common.py): a cue whose parenthetical is too long for one line arrives as two `name` lines (`קב"שית (בחוסר` then `אמון)`), and one item per name line makes the second half a junk name row. In `group_into_items`, a `name` arriving when the last item is already a `name` with an **odd** bracket count is appended to it instead. After the buffer flushes, a trailing `name` item can only mean the previous line was also a name with nothing between them, so no extra adjacency check is needed. Count-based rather than nesting-based for the same reason as above: at this point in the pipeline the pair may still read `)…(`.
- **Scene-heading strip** (`_strip_scene_heading` in parser_common.py): Hebrew screenplays use slug-line headers like `"פנים. יום. סלון ביתו של ג'ק"` (interior/exterior + time + location) right after the title and at every scene break. These don't belong in the analysis table. Lines matching `^(פנים|חוץ)\.\s` are handled in `lines_to_items` *before* `group_into_items`, so they don't get merged with adjacent stage_directions. **But writers often fold the opening action into the slug line**, bold, so it classifies as a stage direction — `"פנים. פיליפ ואליזבת נמצאים בחדר הכביסות הצמוד למוסך."` (האמריקאים), `"פנים. חדר מעונות. יום. לוגן יושב וקורא עיתון. רורי … דופקת"` (בנות גילמור) — and dropping the whole line lost the scene's opening note (the "opening stage notes missing" bucket of the review; 5 of the 12 slug-matching corpus lines are this shape, 8–14 words; the 7 true slugs are 3–6). Word count alone can't separate them at six words (`"פנים. יום. ביתה של מאדאם טורבל."` vs `"פנים. בית. סנדרה וסמואל אוכלים במטבח."`), so the rule is structural: walk the period-separated segments from the start and skip every one of ≤ `_SLUG_SEGMENT_MAX_WORDS = 3` words (the slug tokens); keep the text from the first longer segment onward if it has ≥ `_SLUG_ACTION_MIN_WORDS = 5` words, otherwise drop the line. A four-word location (`"מחוץ למועדון הסטנד אפ"`) still drops; so does the four-word action in אנטומיה של נפילה — the price of not inventing a location-vs-action classifier.

- **Do not modify column widths.** A–M stay exactly as the template defines them (A–G + M are explicit; H–L have no `column_dimensions` entry and inherit the default ~8.43, which is correct). Creating dim entries for H–L (even to set `hidden=True`) drifts the layout and shifts the safe scale.
- **`ws.print_area = f"A1:M{last_item_row}"`** is set in `fill_template`. Belt-and-suspenders with the scale fix: pins the right edge at column M and the bottom edge at the last filled row so LibreOffice has no excuse to emit a right-overflow or trailing-blank phantom page. Earlier iterations argued against setting this — that guidance is obsolete now that we're not hiding columns; leaving it set is harmless and defensive.
- **Do not re-enable `fitToPage`.** LibreOffice's xlsx fit-to-width with `fitToHeight=0` and our manual breaks ends up auto-scaling to ~42%, far smaller than the column-width math predicts — pages render with ~30% of vertical space empty. Forcing an explicit scale is the only way to get predictable vertical packing.
- `page_content_height_pt` (in `_layout_profile()`) is the per-page vertical budget. Theoretical max derivation: A4 landscape = 595pt tall, minus 0.75" T+B margins (108pt) = 487pt physical usable; at scale 55% that's 487 / 0.55 ≈ 886pt of logical row-height room per page. Locally the full 886pt is used; **Lambda uses 842pt** (~5% buffer, selected by `CELL_FONT_OVERRIDE` being set). The buffer was added when multi-line stage_directions clipped at the page bottom — in hindsight that was the character-count undercount in the row heights (see the row-height bullet below), which is now fixed, but the buffer hasn't been re-verified on Lambda so it stays. If you change `_PRINT_SCALE_PCT`, recompute both budgets. `_set_page_breaks_keeping_name_with_dialogue` walks rows accumulating heights and inserts a manual `Break` *before* any row that would overflow, with a look-ahead that treats `name + dialogue` as one indivisible unit. **Drift symptom:** the last row of a page reappears alone at the top of a near-empty page — the walker is under-counting `HEADER_ROWS_HEIGHT_PT` or `page_content_height_pt`, letting one too many rows onto a page, and LO inserts its own break that pushes the orphan over. Verify `HEADER_ROWS_HEIGHT_PT = R1+R2+R3+R4` matches the actual template (R3 is post-`_spread_numbered_list_cell` 174, not the template's raw 111).
- **Widow control on the final page** (`_MIN_LAST_PAGE_FILL_RATIO = 0.25` in filler.py): distinct from the drift symptom above — here the walker is right and the content genuinely doesn't fit. In `השור הזועם` page 6 filled 878 of 886pt, so the closing 28pt stage_direction had nowhere to go and got its own page at **0.16% ink**. The page *count* can't be improved: greedy packing is optimal for minimising pages when the row order is fixed (holding a unit back can never let more fit later), so 7 pages is the true minimum. The fix is to rebalance rather than repack — when the last page holds less than 25% of the budget, units are pulled back from the penultimate page until it does. Only the last two pages move, and the guard `page_height(last) + unit <= page_budget` means it can never add a page. Result: last page 28pt → 234pt (0.16% → 1.75% ink), page count unchanged; `אייל קטן` likewise went 182pt → 238pt. Nine other sample files were untouched. **Telling the two causes apart:** if the orphan row is one the walker assigned to the *previous* page, it's metric drift (retune the budget); if the walker itself broke before it, it's a widow (this rule).
- The greedy pack in `_set_page_breaks_keeping_name_with_dialogue` tests "is this the first unit on the page" with `if page`, **not** by comparing the running height against `HEADER_ROWS_HEIGHT_PT`. The old comparison silently suppressed a break whenever a page-2+ unit left the accumulator below 324.75pt, letting the next unit overflow the page. A single unit taller than a whole page still gets a page to itself — it cannot be split.
- Phantom-row cleanup: after filling, delete any `row_dimensions` entries beyond `last_item_row`; openpyxl can leave styled empty rows behind that LibreOffice renders as blank trailing pages. Note the template's actual `max_row` is **not** the visually obvious last row — use `ws.max_row` dynamically (see `_trim_or_extend_rows`).
- **Row height = measured wrap × line height + padding** (`_estimate_row_height` → `_wrapped_line_count` in filler.py). The wrap count is a greedy word-wrap simulation with real glyph widths: Pillow loads `NotoSansHebrew-Regular.ttf` / `-Bold.ttf` (names and stage directions are set bold, which is wider) and packs words against `_COLUMN_B_INNER_WIDTH_PT = 338.5` — column B's cell borders sit at x=580.0/766.2 in the rendered PDF, 186.2pt at the 55% scale. LibreOffice lays Noto out 0–4% narrower than Pillow's advance widths (bold 6–12%), so the capacity is divided by the p95 ratio (`_LO_WIDTH_RATIO`): the estimate errs toward one line too many, never one too few. A word wider than the column is broken mid-word, as LO does. Line height is 24pt per wrapped line; padding per (kind, length) tier: name 4, dialogue short 4 / long 10, stage short 4 / long 6 ("short" = ≤3 lines, "long" = ≥4, `_LONG_LINE_THRESHOLD`).
  - **Why not a character count.** The previous estimator assumed 50 characters per line. The real capacity is 40–44 regular / 32–39 bold and varies with the letters (ש/ם are wide, י/ו narrow), so every cell in the 36–50-character band got a one-line row and rendered two — the second line squeezed under the first and overlapped by the next row. That was the "טקסט חתוך" bucket of the review, and it was systemic: 103 of 104 corpus outputs had at least one such cell; 1,026 squeezed line pairs in total. Detect it with the grid: a text line whose bbox bottom passes the horizontal grid line below it has overflowed its row.
  - **Fallback and dependencies.** If Pillow or the font file is missing, `_FALLBACK_CHARS_PER_LINE` (40 regular / 33 bold) is used. `_wrap_font` looks in `%WINDIR%/Fonts`, `/usr/share/fonts/truetype/noto` (Debian `fonts-noto-core`, installed in Dockerfile.lambda), `/usr/share/fonts`, `/usr/local/share/fonts`, `~/.fonts`. Pillow is pinned in requirements.txt because row heights now depend on it (pdfplumber only pulled it in transitively before).

- **One layout profile for both environments** (`_layout_profile`). Hebrew glyphs render in Noto Sans Hebrew in both: locally LibreOffice picks it as the Hebrew fallback for Calibri, on Lambda `CELL_FONT_OVERRIDE` names it outright. The old split (a "Carlito" profile locally with 24pt/50 chars, a bumped "Noto" profile on Lambda with 27pt/46 chars and bigger padding) was tuned around the character-count undercount above, not around a real font difference. **Measured floor:** when a cell is too short LO packs lines at their natural pitch, 10.0pt rendered = **18.2pt logical**; 24pt per line is ~30% headroom, which the cell's `distributed` vertical alignment spreads between the lines. 27.3pt per line was tried and cost 19% more pages for no visible gain. The only remaining environment difference is the per-page budget: 886pt locally (487pt physical / 0.55) vs 842pt on Lambda — the ~5% buffer added when cells clipped at the page bottom. With measured row heights it is probably unnecessary, but it hasn't been re-verified on Lambda, so it stays.
  - The `CELL_FONT_OVERRIDE` env override exists because LibreOffice on Debian was picking NotoSansDevanagari as the Hebrew fallback under Carlito and rendered tofu. Setting it to `Noto Sans Hebrew` fixes the glyphs.

- **CELL_FONT_OVERRIDE must also pin `readingOrder=2` on every template cell.** The template's static labels (e.g. "נסיבות מקדימות:", "טקסט + אובייקטים פנימיים + סימון ביטים") rely on font-based bidi inference. Once we swap the font, that inference shifts and bidi-neutral characters drift to the wrong end — observed: the leading נ of "נסיבות" detaches and reads as "סיבות מקדימות"; the two `+` signs jump to the visual front, producing "+ + טקסט אובייקטים פנימיים סימון ביטים". The font-override loop in `fill_template` rewrites both `cell.font` and `cell.alignment` (preserving the existing horizontal/vertical/wrap/indent settings, only forcing `readingOrder=2`).
- Numbered-list header cell D2 (merged D2:E3) is patched by `_spread_numbered_list_cell`. The template uses `vertical=distributed` to spread `.1 / .2 / .3 / .4 / .5` evenly across the cell — Excel honors that, LibreOffice doesn't (lines cluster). The fix encodes the spacing in the text itself (blank line between each number), switches the cell to `vertical=top`, and bumps R3 to 174pt so the now-9-line content fits. `HEADER_ROWS_HEIGHT_PT = 324.75` (R1=52.5 + R2=42 + R3=174 + R4=56.25) matches the actual template heights — the page-break walker uses this as the page-1 starting offset. Drift symptom if this undercounts: orphan-last-row on a near-empty page.
- **Breathing blanks** (`_add_breathing_blanks` in filler.py, called at the very start of `fill_template`): inserts a `{"type": "blank"}` row at the top of every output (so content doesn't butt against the header), and one between the opening stage_direction block and the first character name when the scene opens on stage_directions. Blanks render as empty template-styled cells at `_MIN_ROW_HEIGHT_PT`. They count toward the page-break walker's row budget like any other row.

## Deployment

Live URL: https://d3jh9ygx0amvge.cloudfront.net/. Source of truth: `github.com/grassmeight/chubbuck`, branch `main`, and it is the only git remote (`origin`). The earlier HuggingFace Space deploy is retired (remote removed 2026-11-07); comments in `Dockerfile.lambda` and `requirements.txt` that mention "the HF deploy" are historical.

The CloudFront distribution (`ENJIWKRFZYLJD`) has **two origins**:
- Default behavior (`/`, `/index.html`, assets) → S3 bucket `chubbuck-static-344550433882`.
- Ordered behavior (`/api/*`, `/health`) → Lambda Function URL.

A push to `main` triggers `.github/workflows/deploy.yml`, which runs all four steps:
1. Build the Docker image (`Dockerfile.lambda`), push to ECR.
2. `aws lambda update-function-code` + wait for `Successful`.
3. `aws s3 sync app/static/` to the static bucket — `*.html` gets `Cache-Control: no-cache`, everything else gets `max-age=86400`. `--delete` cleans up renamed/removed assets.
4. `aws cloudfront create-invalidation --paths /*` (fire-and-forget; propagation 1–5 min).

Steps 3 and 4 were added 2026-05-19 (commit `c1e1d13`). Before that the workflow only updated Lambda, which meant any change under `app/static/` (or `index.html`) would deploy a fresh Lambda image but leave CloudFront serving the previous static origin — symptom: UI doesn't match what's in the repo even though the Actions run is green. **If you see this, the first place to look is the "Sync static assets to S3" / "Invalidate CloudFront cache" steps in the latest run** — Lambda update success ≠ user-visible UI update.

Auth is via OIDC: the IAM role `chubbuck-github-actions` (ARN in repo variable `AWS_ROLE_ARN`) trusts only `repo:grassmeight/chubbuck:ref:refs/heads/main`. The role has scoped permissions for ECR push, Lambda update on `chubbuck`, S3 PutObject/DeleteObject/ListBucket on the static bucket, and `cloudfront:CreateInvalidation` on this specific distribution — nothing else. Defined in `infra/github_oidc.tf`; trust target is set via `github_repo` in `infra/terraform.tfvars` (gitignored).

The S3 `uploads` bucket (`chubbuck-uploads-344550433882`) is separate and only reachable via the presigned-PUT flow in `app/main.py` (`/api/upload-url` + `/api/convert-s3`); the GitHub Actions role has **no** access to it.

## Conventions & Gotchas

- Development environment: Windows 11, PowerShell. Use PowerShell syntax in shell commands (`$env:VAR`, `;` for sequencing — `&&` is not available in Windows PowerShell 5.1).
- Python 3.14. Some packages need pinned older versions (notably `python-bidi<0.5`).
- Don't open the test xlsx (`טבלת ניתוחים ריקה.xlsx`, `_*.xlsx`) in Excel while running scripts — Excel's lock prevents openpyxl from saving.
- The classifier needs both bold *and* an underline rect to call something a name. If a PDF's underline is encoded as a rendered glyph rather than a rect/line, classification will mis-fire and every line will look like a stage direction. Verify with a single-page sample before debugging upstream.
- `parser.parse(path)` is the only entry point used by `main.py`; `parse_pdf` and `parse_docx` are re-exported from `parser.py` for tests but should not be wired into new callers — let the dispatcher handle suffix routing.

### Known open issues (from the 2026-11-07 corpus review)

Things the review surfaced and deliberately left alone. Check here before "fixing" one of them in passing.

- **A third script format is unsupported by design.** `סצנה לאודישן מצולם אסנת.pdf` has no bold or underline anywhere; names, dialogue and stage notes are encoded purely by horizontal position in three nested right-margin columns (names at x1≈327, dialogue ≈427, stage notes ≈540 on that file). The current classifier reads every line as dialogue or stage note and finds zero names. It fits the pipeline (only the classification step would change: detect "no bold anywhere", cluster right edges per document, assign by column), but with one sample it was judged not worth adding. If more arrive, that is the design.
- **Two files parse to almost nothing:** `חיזור גורלי- אלכס ודן.docx` yields 2 items (1 name, 1 dialogue) and `בלו ולנטיין- דין וסינדי ברכב.docx` finds a single name. Their character names aren't recognised, so the preamble trim or the dialogue merge swallows the scene. Not investigated.
- **Stage notes still lost on purpose:** the four-word opening action in `אנטומיה של נפילה` (`"פנים. בית. סנדרה וסמואל אוכלים במטבח."`, under the slug-strip minimum) and two notes in `חצות בפריז` (the justified-doc guard fires at 0.58 on what is really a centered script with many long lines; the per-line rescue is intentionally not applied under that guard). Fixing the latter needs a better justified-vs-centered discriminator (justified lines share an identical x0; centered ones don't).
- **Parenthetical cues inside a speech stay in the dialogue** (`"אל תדאגי (מלטף את צווארה) עכברושים לא…"`). The reviewer hasn't asked for them to be split out; doing so would be a new behaviour, not a fix.
- **Character-bio and premise paragraphs** formatted like stage notes (`אהבה נושכת`, `נאמנות גבוהה`) are promoted to an opening stage_direction block. That is the author's formatting, not a parser error.
- **Over-tall cells, not clipped ones, are the remaining layout imperfection.** The width model divides by the p95 LO/Pillow ratio, so a regular-weight line near the capacity sometimes gets one more estimated line than it renders; the `distributed` alignment spreads the slack. Tightening toward the median ratio would trade that for occasional clipping, which the reviewer flagged as the worse failure.
- The uncommitted modification to `טבלת ניתוחים ריקה.xlsx` in the working tree predates the review and was not examined.
